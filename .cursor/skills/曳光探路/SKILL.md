# 曳光探路

对应《程序员修炼之道》的 **Tracer Bullets**：先打一发能贯穿系统的薄弹，用真实反馈校准瞄准，再加厚。

## 何时用

- 新功能、方向或集成点不确定
- AI 倾向于先生成完整分层/目录骨架
- 需要区分「可保留的薄路径」与「可丢的学习原型」

## 步骤

1. **澄清目标**（最多问清这些）  
   - 成功长什么样？（一条可演示路径即可）  
   - 固定约束是什么？（语言、现有模块、不能动的边界）  
   - 最不确定的一点是什么？

2. **画薄路径**  
   用 3–7 步写出端到端路径，例如：`入口 → 校验 → 领域动作 → 持久化/外部调用 → 响应`。  
   每步只保留让路径通得所需的最小代码。

3. **实现曳光弹（可保留）**  
   - 真实接线，走真实边界；可打桩外部依赖，但主路径要通。  
   - 遵守悟仙契约：一次一轴、知识唯一、显式错误。  
   - **不要**同时实现完整错误矩阵、全部 UI 态、过早抽象。

4. **若只需学习：单独开「可丢原型」**  
   - 标明 `SPIKE / THROW-AWAY`。  
   - 验证完：提炼结论，再按结论重写或并入曳光路径；禁止把原型直接当产品扩。

5. **验收**  
   - [ ] 路径可运行或可演示  
   - [ ] 变更范围小、边界清楚  
   - [ ] 下一步加厚的优先级明确（列 3 条以内）

## 输出格式

```markdown
## 曳光目标
...

## 薄路径
1. ...
2. ...

## 本轮改动
- 文件/模块：...
- 未做（有意推迟）：...

## 验证方式
...

## 下一步加厚（按优先级）
1. ...
```

## 禁止

- 先堆完整 Clean Architecture 空壳再填逻辑  
- 把 spike 原型不经重写直接产品化  
- 一次会话改多个无关轴
